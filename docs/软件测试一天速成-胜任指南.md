> **老师说明（请先读）**  
> 你好，我是按「AI 智能体老师」方式写的这份手册。  
> **一天能达成什么：** 搞懂测试在干什么、会写用例、会测接口和页面、会报 Bug、面试能讲清楚——**够应付初级/实习/校招测试岗的基础面试和上手**。  
> **一天不能达成什么：** 成为资深测试专家、自动化架构师、性能/安全深度专家。那些需要项目练手。

> **你的优势：** 你有 Java/Spring、Postman、MySQL、Kafka、实习 AI 工具测试经验——这是「**懂开发的测试**」，比纯理论测试更有竞争力。本手册会**放大这个优势**。

## 一、测试岗位到底在做什么？（15 分钟读懂）

### 1.1 一句话

> **在软件交给用户之前，按需求找出它哪里不对，并推动修好。**

你不是「点点点」，你是**质量把关**：需求对不对、功能对不对、数据对不对、体验顺不顺。

### 1.2 和开发的关系（面试常问）

| 角色 | 关注点 |
|------|--------|
| **开发** | 怎么实现功能 |
| **测试** | 实现得对不对、有没有漏场景、会不会把别的功能弄坏 |

**好测试**不是开发敌人，是帮团队**少背锅、少线上事故**的人。

### 1.3 测试常见类型（知道名字即可）

| 类型 | 人话 |
|------|------|
| **功能测试** | 功能能不能用、符不符合需求 |
| **回归测试** | 改了一处，别的地方有没有坏 |
| **冒烟测试** | 新版本能不能先「跑起来」，再细测 |
| **接口测试** | 不通过界面，直接测后端 API |
| **性能测试** | 人多、数据多时卡不卡（入门了解即可） |
| **兼容性测试** | 不同浏览器、手机是否正常 |

**你今天主攻：** 功能测试 + 接口测试 + 用例设计 + Bug 报告。

## 二、测试思维四件套（核心，全天都要用）

### 2.1 等价类划分

**思想：** 把输入分成「一类一类」，每类抽一两个代表测，不用全测完。

**例子：登录密码 6～20 位**

| 等价类 | 例子 | 预期 |
|--------|------|------|
| 太短 | 5 位 | 失败，提示 |
| 合法 | 10 位 | 成功 |
| 太长 | 21 位 | 失败 |
| 空 | 不填 | 失败 |

### 2.2 边界值

**思想：**  bug 最爱躲在**边界**上（最小、最大、刚好超一点）。

同上：测 **5、6、20、21** 位，而不只测中间「123456」。

### 2.3 场景法（业务流程）

**思想：** 按用户真实操作顺序串起来测。

**例子：新闻 App**

注册 → 登录 → 看推荐 → 点一条 → 收藏 → 再看推荐是否变化 → 退出 → 再登录历史是否还在。

### 2.4 异常 / 负面测试

**思想：** 不只测「对的」，还要测「错的」。

- 断网、弱网  
- 重复点击提交  
- 未登录访问要登录的页面  
- SQL 特殊字符、超长字符串、表情符号  
- 并发两人改同一条数据（了解即可）

**口诀：** **正常路径 + 边界 + 异常 + 全流程**。

## 五、第二节：接口测试 Postman（10:00-12:00）

你有 Spring Boot 项目，这是**最快能上手**的测试技能。

### 5.1 接口测试在测什么

| 测什么 | 例子 |
|--------|------|
| 状态码 | 200、401、404、500 |
| 返回 JSON 字段 | 有没有 token、userId |
| 业务规则 | 错误密码不能登录 |
| 边界参数 | message 为空、chatId 不存在 |
| 鉴权 | 不带 token 是否 401 |

### 5.2 Postman 最小流程

1. 新建 Collection「百味智厨」  
2. 先调 `POST /api/auth/login` 拿 token  
3. 在 Collection 变量里设 `token`  
4. 其他请求 Header：`Authorization: Bearer {{token}}`  
5. **SSE 接口** EventSource 不好在 Postman 测 → 用浏览器或前端页测，Postman 测 sync 接口

### 5.3 百味智厨建议测的接口（有项目就开本地）

| 接口 | 测什么 |
|------|--------|
| POST /auth/register | 重复注册、短密码 |
| POST /auth/login | 对错密码 |
| POST /chat/conversations | 未登录、正常创建 |
| GET /chat/conversations/{id}/messages | 越权：A 用户能否看 B 的会话 |
| GET /ai/chef_app/chat/sync | 正常 message、空 message |

### 5.4 断言（Tests 标签页，了解语法即可）

```javascript
pm.test("状态码 200", function () {
    pm.response.to.have.status(200);
});
pm.test("有 token", function () {
    var json = pm.response.json();
    pm.expect(json.token).to.exist;
});
```

### 5.5 ✅ 实操（90 分钟）

1. 启动后端 + PostgreSQL  
2. Postman 跑通：注册 → 登录 → 建会话 → 查历史  
3. 故意错 token 测 401  
4. 截图保存（面试可展示「我有接口测试习惯」）

### 5.6 和你简历的连接（面试背）

> 我有 Spring Boot 开发经验，接口测试用 **Postman** 做正常/异常参数验证；百味智厨和新闻推荐项目都做过**前后端联调**，能从接口层快速定位是前端、后端还是数据问题。

## 七、第四节：数据库验证（14:30-16:00）

测试岗**很加分**：会用 SQL 核对后台数据。

### 7.1 什么时候查库

| 场景 | 查什么 |
|------|--------|
| 注册成功 | `sys_user` 是否多一行 |
| 发消息后 | `chat_message` 是否有 user/assistant 记录 |
| 推荐埋点 | MySQL 行为表是否有记录；Kafka 另说 |

### 7.2 百味智厨示例 SQL

```sql
-- 用户是否注册成功
SELECT id, username, created_at FROM sys_user WHERE username = 'test_user';

-- 某会话消息条数
SELECT role, LEFT(content, 50), created_at
FROM chat_message
WHERE conversation_id = '你的chatId'
ORDER BY created_at;

-- 会话是否归属用户（越权测试后核对）
SELECT c.id, c.user_id, c.title
FROM chat_conversation c
WHERE c.id = '会话id';
```

### 7.3 数据测试思维

- 界面显示 3 条历史 → 库里是否 3 条  
- 删除后 → 逻辑删除 `is_deleted` 还是物理删  
- 统计报表 → SQL 聚合是否和页面一致（你新闻项目 ECharts 故事）

### 7.4 ✅ 实操（45 分钟）

注册一个测试账号，聊 2 轮，用 SQL 核对 `chat_message` 条数和内容是否对得上。

### 7.5 面试话术

> 功能测试之外，我会用 **SQL 做数据校验**，确认接口和页面不是「假成功」；这和我的大数据/SQL 背景是相通的。

## 十、第七节：测试岗面试 15 题（19:00-20:30）

每题用下面【答】练口头回答，不要背字面，理解意思。

---

**1. 什么是软件测试？**

【答】在软件上线前，根据需求验证功能、性能、易用性等是否达标，发现缺陷并跟踪修复，降低线上风险。

---

**2. 测试用例设计方法你知道哪些？**

【答】等价类、边界值、场景法、错误推测。实际工作里常组合用：先场景串流程，再对输入做边界和等价类。

---

**3. 冒烟测试和回归测试？**

【答】冒烟：新版本能不能先快速测一遍主流程，不行就打回。回归：改 bug 或加功能后，把相关老功能再测一遍，防止改坏。

---

**4. Bug 生命周期？**

【答】新建 → 指派开发 → 修复 → 待验证 → 测试关闭（或 reopen）。不同公司工具不同，流程类似。

---

**5. 严重程度 vs 优先级？**

【答】严重程度看影响多大；优先级看多快要修。致命不一定先发版，但一般 P0 要优先。

---

**6. GET 和 POST 测接口时要注意什么？**

【答】GET 参数在 URL，注意编码和长度；POST 看 body 格式 JSON 还是表单；都要测鉴权、空参数、非法类型。

---

**7. 你怎么测一个从没见过的系统？**

【答】先读需求或产品说明 → 画主流程 → 写用例 → 冒烟通主路径 → 再细测边界和异常 → 查库核对数据。

---

**8. 开发说「我这边没问题」你怎么沟通？**

【答】带复现步骤和截图/日志，客观描述预期与实际；必要时请产品确认需求；不吵架，对事不对人。

---

**9. 测试需要会代码吗？**

【答】初级不强制，但**会看日志、会 Postman、会简单 SQL** 效率高很多。我有 Java 开发基础，能读接口代码辅助定位，这是优势。

---

**10. 手工测试和自动化测试？**

【答】手工适合探索性、新功能、UI 体验。自动化适合回归、接口稳定场景。入门先手工+接口，再学 pytest/JMeter 等。

---

**11. 你怎么保证测试不漏？**

【答】不可能 100% 不漏。靠需求评审、用例评审、优先级（先 P0）、回归、生产监控。目标是**风险可控**，不是测遍所有组合。

---

**12. 简历是开发，为什么做测试？**（见复习计划测试岗版本）

【答】实习做过指标测试，项目里长期联调；我更擅长从验收标准出发保障质量；开发背景让接口和数据测试更高效，不是做不了开发。

---

**13. 什么是接口测试？**

【答】绕过 UI，直接对 API 发请求，验证状态码、返回体、业务规则、鉴权。工具常用 Postman。

---

**14. 什么是兼容性测试？**

【答】不同浏览器、分辨率、操作系统下功能是否正常。至少测 Chrome + Edge 或主流安卓机。

---

**15. 检出率怎么测？（结合你实习）**

【答】准备标注好「应检出」的测试集，跑工具结果，统计正确检出数/应检出总数，另计误报漏报，输出报告推动修复。

## 十二、一天之后如何「胜任」初级测试岗

### 12.1 你能胜任的工作内容

- 按用例执行**手工功能测试**  
- 用 **Postman** 做接口测试  
- 用 **SQL** 核对关键数据  
- 提交**规范 Bug 单**  
- 参与**冒烟、回归**  
- 写简单**测试报告**（通过数、遗留问题）

### 12.2 入职第一周建议（提前有数）

1. 熟悉产品和测试环境账号  
2. 要需求文档或原型，补用例  
3. 跟老测试走一遍主流程  
4. 弄清 Bug 提交流程  
5. 每天同步测试进度和风险  

### 12.3 第二天起继续补（不在今天范围内）

| 天数 | 补什么 |
|------|--------|
| 第 2 天 | Charles/Fiddler 抓包、JMeter 入门 |
| 第 3 天 | 用例管理工具、测试报告模板 |
| 第 4-7 天 | 对你应聘公司的业务做专项用例 |
| 第 2 周 | 接口自动化（Postman Collection / pytest） |

## 十三、老师给你的「一天通关」自检清单

打印或复制，做完打勾：

```
□ 能口头说出测试是干什么的
□ 会用等价类、边界值各举 1 个例子
□ 手写至少 5 条规范测试用例（含步骤+预期）
□ Postman 跑通登录+至少 2 个业务接口
□ 故意测 1 次 401/参数错误
□ 页面功能清单测过百味智厨或任意 Web 项目
□ 会用 SQL 核对至少 1 张业务表
□ 写过 2 份完整 Bug 单
□ 每个简历项目能讲 30 秒「我怎么测」
□ 15 道面试题能答上来 10 道以上
□ 准备好「为什么做测试」的回答
```

**≥ 9 项打勾：** 可以投初级测试岗并参加面试。  
**< 7 项：** 明天补 Postman + 用例 + Bug 单三块。

## 十五、老师最后叮嘱

1. **诚实：** 一天是**入门胜任**，面试别说「三年测试专家」。说「有开发基础 + 实习测试 + 系统学过用例和接口测试」。  
2. **扬长避短：** 多讲 Postman、SQL、数据校验、AI 检出率；少和纯测试科班比「测过多少 App」。  
3. **带着作品去面试：** Postman 截图、用例 Excel、Bug 单样例，比空口说强十倍。  
4. **今天重在练手：** 读 1 小时不如 **Postman 测 1 小时**。
