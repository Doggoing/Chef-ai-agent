#### 下午：项目口述稿（2 分钟，背熟）

> 这是一个工业场景的**离线与实时一体化数仓**项目。离线侧我用 Hive 建 ODS-DWD-ADS 分层，Spark SQL 做 ETL 和指标加工，ADS 对接 Power BI 给管理层看板。实时侧用 **Flink CDC** 监听 MySQL binlog 同步配置表，结合**广播流**做维度关联；事实流和维表流用**水位线 + Interval Join** 解决延迟不一致。维表先落 **HBase**，再通过**异步 I/O** 把热点维度加载到 **Redis**，降低 HBase 读压力。DWS 聚合结果写入 **Doris** 供分析查询。我还参与了**统一字段规范**和 **HDFS 小文件合并**优化。

#### 下午：深挖 5 题（含包装答法）

**Q1：你在项目里具体负责什么？**  
> 我**主要负责**实时链路这块：Flink CDC 采集、维表广播、Interval Join 关联，以及维表 HBase+Redis 的异步缓存方案；离线侧参与 DWD/ADS 层 Spark SQL 开发和 Power BI 看板对接。

**Q2：Flink CDC 原理？**  
> 通过 Debezium 等机制读 MySQL binlog，先做全量快照再增量订阅；下游收到 INSERT/UPDATE/DELETE 变更事件，可以实时更新维表或写入 Kafka/HBase。

**Q3：为什么维表要 HBase 又要 Redis？**  
> HBase 适合海量维表、列式宽表存储；但随机读延迟高。Redis 做**热点维表缓存**，异步 I/O 批量加载，读路径先 Redis 再 HBase，**显著降低** HBase 压力——这是我们项目里的核心优化点。

**Q4：Interval Join 是什么？**  
> 两条流事件时间差在一个区间内才匹配，比如订单流和支付流允许 5 分钟内关联，避免无限等待；配合 watermark 处理乱序。

**Q5：小文件过多怎么处理？**  
> Spark 输出控制 `coalesce/repartition`、Hive 合并小文件、按天分区、定期 compaction；源头控制 Flume/Sqoop 批次大小。

**Q3：协同过滤你怎么做的？**

**Q4：Redis 存什么结构？**  
> 用户推荐 List、热门榜 ZSet（score=热度）、用户偏好 Hash（类别权重）；TTL 按业务设。

**Q5：Spark Streaming 和 Flink 选型？**  
> 本项目实时性要求秒级，和 Spark 离线生态统一，用 Streaming 开发成本低；若毫秒级会选 Flink。

#### 一、工业数仓（6 个，主推 ★1 ★2）

**★故事 1：双流延迟不一致，Join 对不上（Interval Join + Watermark）**

| 项 | 内容 |
|----|------|
| **背景** | 实时链路要把**订单事实流**和**支付/状态维表流**关联，两边到 Kafka 的时间差经常有几分钟 |
| **问题** | 普通 Join 要么永远等不到右流，要么乱序导致关联失败，DWD 层数据大量缺失 |
| **动作** | 在 DWD 注入 **Watermark** 容忍乱序；采用 **Interval Join**，只在「事件时间差 N 分钟内」才匹配；维表变更仍用 **广播流** 下发到各并行度 |
| **结果** | 关联成功率明显提升，延迟在可接受窗口内的订单都能进下游；任务不再因单条迟到无限挂起 |

**面试追问准备：** Watermark 怎么设？设太大延迟高，太小丢数据——可以说「结合业务允许延迟和业务方一起定了 2～5 分钟窗口」。

---

**★故事 2：维表查 HBase 太慢，拖垮实时任务（HBase + Redis 异步 I/O）**

| 项 | 内容 |
|----|------|
| **背景** | 维表数据落在 **HBase**，事实流每条都要补维度字段 |
| **问题** | 高峰期 HBase 随机读 QPS 高，Flink 算子背压，任务延迟从分钟级涨到十几分钟 |
| **动作** | 维表变更仍 **CDC → HBase** 全量落库；读路径改为 **先查 Redis**，miss 再回源 HBase；用 **异步 I/O** 批量加载热点维到 Redis，避免同步阻塞 |
| **结果** | 热点维度命中率提高，HBase 读压力下降，Flink 任务恢复稳定，端到端延迟回到预期 |

**面试追问准备：** 缓存一致性？「维表更新先写 HBase，再异步刷新/删除 Redis 对应 key」。

---

**故事 3：Spark ETL 数据倾斜，任务跑不完**

| 项 | 内容 |
|----|------|
| **背景** | 离线 DWD 某张表按**设备 ID** 聚合，少数设备上报量特别大 |
| **问题** | Spark 个别 partition 特别大，Stage 卡在最后几个 task，跑几个小时 |
| **动作** | 对热点 key **加盐** 打散再聚合；小维表用 **Map Join（广播）**；同时检查分区字段是否合理 |
| **结果** | 最慢任务从数小时降到可接受范围，ADS 指标准时产出 |

| **动作** | ① 上线 **QueryRewriter**，把口语改写成利于检索的 query；② 入库阶段用 **KeywordMetadataEnricher** 补关键词 metadata；③ 调整 Markdown **切块粒度**，避免一条 chunk 过长过杂；④ 菜谱类问题走 **doChatWithRag**，与普通闲聊分离 |
| **结果** | 固定测试集上回答明显更贴知识库，胡编减少；bad case 可追溯到「检索片段」是否相关 |

**面试追问：** 和 fine-tuning 比？「业务知识变动频繁，RAG 改文档即可，成本低」。

#### 六、60 秒口述示例（数仓 ★2，可直接背）

> 实时数仓里维表在 HBase，事实流每条都要关联维度。高峰期 HBase 随机读太多，Flink 出现严重背压，任务延迟从几分钟拖到十几分钟。  
> 我的做法是全量维表仍落 HBase，读的时候 **先 Redis、再 HBase**，并用 **异步 I/O** 把热点维度预热到 Redis。  
> 上线后 HBase 压力明显下降，任务恢复稳定，维表关联延迟回到业务能接受的范围。  
> 如果追问一致性，我会补充：维表变更先写 HBase，再刷新或删除 Redis 里对应 key。

| 指标测试 | 业务 KPI | 实习检出率、推荐点击率抽样 |

#### 11.6.3 常问三连 & 标准答

**Q1：你负责哪些模块？**

> 按项目选一个最熟的展开 30 秒，例如百味智厨：  
> 「**我主要负责** AI 核心链路：大模型接入、RAG 知识库、Tool/MCP、ReAct 智能体，以及用户会话持久化和相关 REST/SSE 接口；前端页面用 Cursor 辅助完成联调。」

**Q2：需求是谁定的？你怎么参与？**

> 「学生项目/实习以导师或产品需求为主；我参与**需求拆解和验收标准编写**，开发前确认接口字段和数据流，开发后用用例验收。」

**Q3：测试怎么做？有自动化吗？」**

> 「**接口用 Postman**，核心链路有 **JUnit 集成测试**（如 RAG 全流程、PG 连通）；数仓/推荐侧重**数据对账和端到端**；实习做过**指标类测试**。上线前会做一轮回归 checklist。」
